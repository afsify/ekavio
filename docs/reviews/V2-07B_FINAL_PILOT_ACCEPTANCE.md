This is an engineering decision for the first controlled pilot, not a general availability or legal certification. No real customer was onboarded for this review. The contemplated pilot is a very small number of invited businesses, with operator-approved onboarding, manual agreements and payments, manual renewals, and PostgreSQL as the sole normal runtime. ## Decision basis

The deployed staging application is live and the local implementation gates pass. Those facts do not make the current operation safe for real customer data: there is no operating scheduled, monitored, encrypted off-provider backup, the actual Neon recovery controls and hosted restore are unproven, and the current backend has shown a 23.0-second cold wake consistent with its historically recorded free/sleeping class. Each backup and hosting item is a mandatory pilot gate. Hosted legacy-source facts, authenticated domain/tenant checks, and operator/monitoring ownership also remain unresolved. No blocker was reclassified as an accepted risk merely to obtain GO.

## Hosting and recovery economics

The minimum candidate is the existing static frontend, one paid always-on Render-compatible Node/WebSocket instance, and managed Neon PostgreSQL. [Render pricing](https://render.com/pricing) listed a paid 512 MB instance from US$7/month at review time; [Neon usage pricing](https://neon.com/blog/new-usage-based-pricing) is variable with compute, storage, and transfer. This is a candidate, not a purchased or selected topology. The real monthly estimate requires the authenticated current service classes, expected compute hours, database usage, connection limit, log retention, and alert/backup storage quotes. No exact bill or pilot availability is claimed. The observed cold wake and absence of an always-on proof make the current backend unsuitable.

The proposed low-cost independent recovery layer is a daily encrypted custom-format PostgreSQL export to a named access-controlled off-provider storage destination, 14 daily plus four weekly copies, alert on failed/overdue backup, and a monthly isolated restore drill. The operator must select the destination, encryption/key custody, scheduler host, notification route, and retention owner. Until a complete cycle and retrieval/restore are evidenced, this is a plan only. The local 12.379-second restore is not a hosted RTO; no hosted RPO/RTO is claimed.

## Security, privacy, and support boundary

The application handles account/contact and membership information, business/customer records, appointment/Queue details, Attendance, Customer Dues, Inventory, security audit events, and manual commercial/payment-record metadata. Those data and backups are sensitive. The application does not call for card/CVV/UPI PIN storage; manual payment records are not gateway settlement proof. Passwords, password hashes, JWTs, refresh credentials, cookies, database URLs, and unnecessary request-body PII must not enter logs or repository artifacts. Access must follow tenant memberships and platform-operator separation; backups and audit archives need named restricted custodians and deletion rules. This is an engineering handling record, not a compliance certification.

The application distinguishes a platform operator for agreements, settlement recording, provisioning, and renewal from a customer tenant. A real pilot additionally needs named people and backups for: commercial verification, outage response, daily backup checks, restore execution, and access/privacy complaints. No staffed support window or 24/7 response is currently evidenced. The roles and triggers are defined in the [pilot operations runbook](../runbooks/PILOT_OPERATIONS.md) and [incident runbook](../runbooks/INCIDENT_RESPONSE.md); they are not yet assigned.
